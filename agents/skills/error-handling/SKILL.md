# Error Handling

- Never write `throw new Error`. `repo-lint` bans it with a per-file allowlist that shrinks as files are swept; a scanned-but-clean entry is reported stale, so clearing a file means dropping its entry in the same change. Keeping one needs a specific reason stated at the site.
- Classify before converting. An invariant something upstream should have guaranteed is `Assert(...)` / `Assert.defined(...)` / `Errors.throwUnexpected(...)`. The Tao author's own data or contract being wrong is `Assert.input(...)` / `Errors.throwUserInput(...)`. A failed device, native module, subprocess, or host capability is `Errors.throwHostEnvironment(...)`.
- The category decides what the reader sees, so it is a product judgment, not a mechanical rewrite. A Tao developer must be able to tell whose mistake an error reports, and should never meet a bare JavaScript error string.
- Classify by where the checked value came from. A value out of the Tao program's own expressions or declarations, or off a persistence or serialization boundary, is the author's; a value produced and consumed inside one pass is an invariant. Most runtime throws turn out to be the author's, because they already name a declaration, field, token, or row.
- Let the existing message decide the framing. A throw already carrying a finished author-facing sentence stays that sentence; only a genuine invariant is reworded into `Expected: …`. Check message survival mechanically after a sweep rather than by eye.
- `Assert` and `Assert.input` take a plain `asserts condition`, so they narrow the operands of the expression you pass — `typeof`, `Array.isArray`, a discriminant check, and a user-defined type guard all narrow through them. Only a helper returning a bare `boolean` fails to narrow, exactly as it would inside an `if`. `Assert.defined` keeps `asserts value is NonNullable<T>`, matching the null check it performs.
- Introducing any assertion call into a function forces explicit type annotations on that function's inference-dependent `const`s (TS7022/TS7006). Annotate locally rather than abandoning the assertion.
- `Assert` builds its message and details eagerly. On a render-hot path whose message is not constant-time, keep a guarded typed throw and say why at the site.
- `Errors.throwUnexpected` and its siblings return `never`, so `if (bad) { Errors.throwUnexpected(msg) }` narrows afterwards while keeping the original sentence. Reach for that before rewording a message to fit `Assert.defined`.
- A `never`-returning call reached through a property chain narrows only when every link carries an explicit type annotation. `TR.Errors.failInvariant(...)` therefore does not narrow, so generated code uses `??` rather than a guard. Generated trees are inside a `tsconfig` include, so this is a real compile error, not a theoretical one.
- Two ratchets run, each with its own per-file allowlist: one bans `throw new Error(`, the other bans a raw `Error` handed to a promise rejection, because a rejection reaches the reader identically. Classify a rejection exactly as you would a throw.
- A third rule keeps one spelling for a thrown Tao error: `Errors.throwUserInput(...)`, `Errors.throwUnexpected(...)`, or `Errors.throwHostEnvironment(...)`, never `throw new Errors.UserInputError(...)` or a bare `throw new UserInputError(...)`. Only the three leaf modules in `packages/shared/shared-src/core` construct the classes; `packages/runtime` is outside the rule because it throws through `TR-errors`. Constructing a class without throwing it — to hand to a rejection, a callback, or a subclass — is still written `new Errors.UserInputError(...)`.
- Assert functions throw typed errors and narrow. `Assert(...)` takes an `Expected: …` fragment; `Assert.input(...)` takes the finished author-facing sentence.
- `packages/runtime` imports nothing from `@shared`, so `TaoRuntime-src/TR-errors.ts` and `TR-assert.ts` mirror the shared error classes and `Assert` the way `TR-switch.ts` mirrors `Switch`. Keep the two in step, import `./TR-assert` directly rather than publishing it on `TR`, and keep the explicit API type annotation, which TypeScript requires for assertion calls.
- Keep runtime error handling reachable from one module. `TR-errors.ts` owns the vocabulary, action-failure history, unowned-failure reporting, redaction, and contained-failure warnings, and `TR.Errors` exposes that whole surface rather than a subset.
- Warn through a shared policy rather than an inline production guard. There are two, and the criterion is whether anything failed: something failed and was swallowed is `warnContainedFailure`, which takes the error; nothing failed but the platform cannot honor a declaration is `warnDesignDivergence`, which takes only a sentence. A design-divergence notice must not be reported as a contained failure.
- Never leak an internal or framework type name into a diagnostic a Tao developer reads.
- Preserve user-facing wording when converting. Diagnostic text and emission order are product surface: prove parity by capturing ordered diagnostics before and after, not by observing that tests pass.
