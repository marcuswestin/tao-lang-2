# DEVENV-WATCHOS-SWIFT-PROBE-FAILS-UNDER-BROAD-LANES — watchOS Swift probe fails under broad lanes

- **Status:** Candidate
- **Section:** External
- **Area:** The `swift -e` probe in `packages/compiler/compiler-tests/watchos.test.ts` ("formats numeric text at ECMAScript notation boundaries in Swift"), run by the `compiler` suite in `verify-changed` and `verify-full`.
- **Impact:** A change that touches no compiler code can fail its local proof on this probe while other lanes saturate the machine. Until 2026-10-06 the test asserted only the exit code, so the failure said `Received: 1` and nothing about why.
- **Evidence:** The host `verify-full` that also produced the project-tooling timeouts in DEVENV-PROJECT-TOOLING-REFRESH-AND-WATCH-TESTS-TIME-OUT-UNDER-BROAD-LANES failed this probe with exit code 1 after 2828 ms, well inside its 30-second cap (`compiler_app-output.log` under `.artifacts/logs/verify-full/2026-10-06T02-23-37-580Z-85528-c3e31204/` in `feat/repo-transfer-urls`). Hosted `Verify` passed the same tree. The recorded failure is therefore a non-zero exit, not a timeout, and the dropped stderr leaves the cause unknown. On 2026-10-06, under a load of 4.3 on 18 CPUs, the probe took 0.19–0.25 s warm in five sequential runs and 1.00–1.04 s with a cold module cache in three runs. Run as 18, 36, and 72 simultaneous copies it took at most 0.34 s, 0.63 s, and 1.23 s. Twenty recorded lane runs of the whole test, compile included, took a median of 2.1 s and at most 6.4 s.
- **Workaround:** Read the node log. The test now matches the whole command result, so a failure prints swift's stderr and the stopping signal. When stderr is a contention symptom and hosted `Verify` is green on the same head, rerun the node alone.
- **Proposed change:** The Developer chose a short-term cap raise and a lasting fix in slice C of the verification speed plan (`Docs/Roadmap/Verification speed plan.md`), which memoises the per-process taxes that broad lanes pay. The cap went from 30 s to 120 s. That is about 100 times the slowest measured probe, and it stays under the runner's 240-second per-test budget, so a hang still fails with the command's own timeout message. Once a failure records swift's stderr, check whether it is a timeout, a module-cache or memory symptom, or a compiler crash before relying on slice C. A larger cap would not have changed the one recorded failure.
- **Dependencies:** DEVENV-PROJECT-TOOLING-REFRESH-AND-WATCH-TESTS-TIME-OUT-UNDER-BROAD-LANES, which was recorded in the same saturated run.
- **Acceptance:** A broad local lane on an unchanged compiler tree passes this probe while other lanes run. Any failure that remains names its cause from swift's own output.
- **Source:** First merge-queue landing, `feat/repo-transfer-urls`, 2026-10-06. The cap was measured and raised on `feat/landing-route-tooling`.
