# DEVENV-HOSTED-CHROME-STARTUP-TIMES-OUT-BEFORE-DEVTOOLS — Hosted Chrome startup times out before DevTools

- **Status:** Candidate
- **Section:** External
- **Area:** Hosted Linux browser verification.
- **Impact:** An admitted browser gate fails before its UI assertions, without enough startup evidence to distinguish a launcher problem from a slow or blocked Chrome child.
- **Evidence:** After integrating main `43012d7bf`, hosted Verify run [37520296658](https://github.com/tao-dev-org/tao-lang/actions/runs/37520296658) on `ec53f0b0a` passed ten partitions and failed partition 1 in `studio-dialog-browser`. The child wait reported `Timed out waiting for Chrome DevToolsActivePort.` after 20 seconds, with no captured output in that error. This does not establish why Chrome failed to expose its port. The failing job is [112463731500](https://github.com/tao-dev-org/tao-lang/actions/runs/37520296658/job/112463731500).
  Two more failures matched it on 2026-10-07, both on `feat/repository-pass-2026-10-07`, which touched no Studio or Chrome code: run [37654585833](https://github.com/tao-dev-org/tao-lang/actions/runs/37654585833) on `6963aa956` partition 15 (`studio-dialog-browser`, [job 112906392825](https://github.com/tao-dev-org/tao-lang/actions/runs/37654585833/job/112906392825)) and run [37657453554](https://github.com/tao-dev-org/tao-lang/actions/runs/37657453554) on `2a0c1f864` partition 6 (`studio-network-simulation`, [job 112916630906](https://github.com/tao-dev-org/tao-lang/actions/runs/37657453554/job/112916630906)). What the three failed partitions' artifacts show:
  1. Chrome stayed alive for the full 20 s each time: PID present, no exit, no signal.
  2. Stderr differed. Run 37654585833 printed two `dbus/bus.cc:405 Failed to connect to the bus` lines in its first millisecond, so the browser process started and then went quiet; those dbus errors are what headless Chrome prints on any runner without a session bus. Run 37657453554 printed nothing. Run 37520296658 predates the startup diagnostics, so its stderr is unknown.
  3. The two runs with machine data had load averages of 9.2 and 8.4 on 4 CPUs (`contended: true`); run 37657453554 peaked at 4.9. Load reached the failing launch from sibling gates, and the 260 s capacity wait in run 37657453554 shows the partition was saturated.
  4. Each failure was the first Chrome launch of its partition, because every partition holds at most one browser gate. So a cold Chrome binary and profile on a loaded runner is as consistent with the data as CPU starvation. Run 37657453554 also started Studio's server and Metro immediately before launching Chrome.
  5. Nothing so far separates CPU starvation, disk stalls (fsync-heavy profile initialization while siblings write), and a stuck child. Passing runs record no Chrome startup duration, so there is no baseline either.
  6. It then turned `main` red twice on 2026-10-07, both times in `studio-metro-refresh` and both before the stall snapshot landed in `fe7a4da74`: run [37661664373](https://github.com/tao-dev-org/tao-lang/actions/runs/37661664373) on `5a2ba4b6c` ([job 112933738128](https://github.com/tao-dev-org/tao-lang/actions/runs/37661664373/job/112933738128)) and run [37668369837](https://github.com/tao-dev-org/tao-lang/actions/runs/37668369837) on `c4b48ea1b` ([job 112953503135](https://github.com/tao-dev-org/tao-lang/actions/runs/37668369837/job/112953503135)), the second with the same two dbus lines. Five failures across three browser gates in two days.
- **Workaround:** None confirmed. Keep the gate admitted and retain its failure.
- **Proposed change:** Startup diagnostics now include the selected executable, PID, profile and bounded first/recent output. Port, HTTP target and DevTools connection waits observe child failure and deadlines independently; unfinished HTTP probes are aborted. Supervised cleanup joins owned processes even after a natural Chrome exit, and secondary cleanup failures retain the startup failure as their cause. Use the next hosted run to diagnose the remaining startup problem rather than extending the timeout without evidence.

  A live Chrome that misses the DevTools deadline on Linux now also appends a procfs stall snapshot to the failure (`ChromeStartupStall.ts`): load average; CPU, I/O and memory pressure (PSI); machine-wide runnable and uninterruptible process counts and the busiest processes; state, thread count and wait channel for every process in Chrome's tree and the state histogram of the browser's threads; and the profile directory's entries. Reading it on the next failure: high CPU pressure with runnable children means starvation, so give hosted Chrome a CPU reservation or start it before the Studio server. High I/O pressure or children in `D` means disk, so put the profile on tmpfs. A quiet tree blocked in a futex or epoll wait with low pressure means a stuck child, so look at its flags and the profile entries. Until one failure carries a snapshot, do not extend the timeout or move the profile.
- **Dependencies:** Chrome installed on the hosted Linux runner.
- **Acceptance:** The hosted dialog browser gate reaches DevTools and passes its interaction assertions. Deterministic startup failures retain the original exit or spawn error, return within their bound and release their owned child and probe resources.
- **Source:** Final verification of `feat/test-process-termination`, 2026-10-06; `StudioCdp.launchChrome` and shared process readiness.
