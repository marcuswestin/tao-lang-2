# Appwrite + Legend State experiment

The adapter uses Appwrite email/password sessions and a DocumentsDB collection for the shared notes contract. Legend State v3 `syncedCrud` keeps optimistic notes in AsyncStorage and persists pending writes for retry. A 30-second poll refreshes remote changes. The installed React Native SDK's `client.subscribe` path reads `window.localStorage` when a socket connects, so this experiment does not use Realtime. It is an Expo Go experiment, not a Tao datasource or an AccessRules implementation.

## Cloud setup

1. Create an Appwrite project and register the iOS bundle identifier and Android package name used by the Expo app. Run `./tao connect appwrite 'Apps/Hosted CRUD'` from the repository root to record the endpoint, project, platform, database, and collection IDs. The server API key stays out of the app bundle.
2. Create a DocumentsDB database and collection. DocumentsDB collections are schemaless; each note document contains `ownerId` (string), `text` (string), `done` (boolean), and `updatedAt` (integer). Add an index on `ownerId` for the list query. The installed `react-native-appwrite@1.1.0` adapter uses its `Databases` document API; verify that API against the chosen hosted Appwrite deployment before treating this setup as working.
3. Enable **document-level security**. Grant collection-level **create** to authenticated users. Do not grant collection-level read, update, or delete; those permissions would bypass each document's owner permissions. The adapter omits explicit document permissions so Appwrite's Client SDK default grants read, update, and delete to the creator.
4. Enable email/password authentication. Sign in before opening notes. The React Native SDK checks the existing session with `account.get()` when restoring it.

Each local persistence key includes the endpoint, project, database, collection, and account ID. After a successful online authentication check, the adapter caches the account ID and email. If a later `account.get()` fails with a transport error, `restore()` returns that cached identity and `open()` allows its notes to load while remote calls retry. A reachable 401 clears the cached identity. Offline restoration is local access to previously cached data, not proof that the server session is still valid; the SDK's session survival across a native restart remains untested.

Sign-out closes open connections before ending the server session and then removes the cached identity. Failed sign-out leaves the cache and server session in place, and the error is returned to the caller. Pending writes are retained under their owner's key for a later sign-in. AsyncStorage is not encrypted; do not put secrets in note text for this experiment.

The `ownerId` field is client-supplied and can be forged or changed with a direct SDK request; the query and adapter-side check are only UI filtering. Appwrite documents say a project user can grant only permissions they have and that Client SDK documents default to creator-only access. Those statements suggest that a forged `ownerId` alone does not let another account read the row, but only hosted hostile-client tests can establish that the intended isolation holds for this collection and SDK version. Any contract requiring server-verified ownership or an immutable `ownerId` needs a server authority, such as an authenticated Appwrite Function that derives the owner from its execution context and owns writes. This experiment has not tested hostile direct requests, offline restart/replay, two-device reconciliation, iOS device behavior, or Expo Go native compatibility. These are required before any provider capability claim.
