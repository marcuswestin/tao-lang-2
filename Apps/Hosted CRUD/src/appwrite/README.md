# Appwrite + Legend State experiment

The adapter uses Appwrite email/password sessions and a free serverless TablesDB table for the shared notes contract. Legend State v3 `syncedCrud` keeps optimistic notes in AsyncStorage and persists pending writes for retry. A 30-second poll refreshes remote changes. The installed React Native SDK's `client.subscribe` path reads `window.localStorage` when a socket connects, so this experiment does not use Realtime. It is an Expo Go experiment, not a Tao datasource or an AccessRules implementation.

## Cloud setup

1. Create an Appwrite Cloud project, such as **Tao Hosted CRUD Demo**, choosing the free serverless option and a region. This is the one manual creation step: a project API key cannot create its own project. Appwrite's organization Partners key can create projects, but cannot configure resources inside them; that still requires a separate project API key. The pilot keeps the simpler single-key setup for an existing project.
2. In project **Settings**, copy the **Project ID** and regional **API endpoint** (an HTTPS URL ending in `/v1`). In the project sidebar open **API Keys**, click **Create API key**, and name it **Tao CLI setup**. Grant `project.read`, `project.write`, `platforms.read`, `platforms.write`, `databases.read`, `databases.write`, `tables.read`, and `tables.write`; add `columns.write` and `indexes.write` if offered. Copy the key when shown.
3. From the repository root, run `./tao connect appwrite 'Apps/Hosted CRUD'`. Enter the endpoint and project ID, then paste the key at the hidden prompt. The command registers the Apple platform `dev.tao.hostedcrudspike`, enables email/password auth, and creates serverless TablesDB database `tao_notes` with Notes table `notes`. It sets required `ownerId` (Varchar 255), `text` (Text), `done` (Boolean), and `updatedAt` (Bigint) columns, an `ownerId` Key index, Row security, and only Users Create table permission. Existing resources are checked before reuse; a mismatched table is refused rather than overwritten.
4. The command writes public IDs to `tao.connections.json` and the key to the ignored, owner-only `.tao/connect-secrets.json`. The key is for local CLI administration and is never bundled into the app. On a later run with the same endpoint and project ID, press Return at the key prompt to reuse the stored key. Run `./tao connect run 'Apps/Hosted CRUD'`, sign in to Expo Go with the Expo account it names, scan the QR code, choose **Appwrite**, and create a test account. The React Native SDK checks the existing session with `account.get()` when restoring it.

Each local persistence key includes the endpoint, project, database, table, and account ID. After a successful online authentication check, the adapter caches the account ID and email. If a later `account.get()` fails with a transport error, `restore()` returns that cached identity and `open()` allows its notes to load while remote calls retry. A reachable 401 clears the cached identity. Offline restoration is local access to previously cached data, not proof that the server session is still valid; the SDK's session survival across a native restart remains untested.

Sign-out closes open connections before ending the server session and then removes the cached identity. Failed sign-out leaves the cache and server session in place, and the error is returned to the caller. Pending writes are retained under their owner's key for a later sign-in. AsyncStorage is not encrypted; do not put secrets in note text for this experiment.

The `ownerId` field is client-supplied and can be forged or changed with a direct SDK request; the query and adapter-side check are only UI filtering. Appwrite documents say a project user can grant only permissions they have and that Client SDK rows default to creator-only access. Those statements suggest that a forged `ownerId` alone does not let another account read the row, but only hosted hostile-client tests can establish that the intended isolation holds for this table and SDK version. Any contract requiring server-verified ownership or an immutable `ownerId` needs a server authority, such as an authenticated Appwrite Function that derives the owner from its execution context and owns writes. This experiment has not tested hostile direct requests, offline restart/replay, two-device reconciliation, iOS device behavior, or Expo Go native compatibility. These are required before any provider capability claim.
